# 业务需求收敛、RFC 模板与架构决策 (Socratic Refinement & RFC Template)

## 1. 苏格拉底式需求收敛协议 (Socratic Refinement Protocol)

当用户给出的需求指令信息不足以支撑写出高精度架构方案时，**严禁凭空脑补核心业务边界，严禁长篇大论凭感觉规划 (Vibe Planning)**。

### 1.1 协议应对准则
1. **基调框架先行**：基于业内成熟通用最佳实践，提炼设计基调框架；
2. **单点聚焦提问机制**：在方案开头明确列出 **2-3 个最关键的决策确认点**：
   - 高并发峰值容忍（吞吐 vs 资源成本）；
   - 读多写少还是强一致性写入（最终一致性 vs 分布式事务）；
   - 超时与降级偏好（快速失败 vs 异步重试）；
   - 冷热数据隔离周期（归档策略与存储介质选型）。
3. **收敛确定性契约**：通过针对性问答收敛出确定性的产品技术契约（Spec Contract），彻底杜绝返工。

## 2. 多层级递进分治与全局闭环串联法则 (Hierarchical Decomposition & Holistic Closure)

> 🚨 **核心红线**：严禁面对复杂系统时进行“单层平铺设计”！必须遵循“向下递进拆解为简单单元，向上串联执行闭合检查”。

### 2.1 向下多层级递进分治 (Top-Down Decomposition)
1. **L1 宏观全景层 (System Scope)**：明确系统核心边界、外部依赖（RPC/中台/第三方）、全局 QPS/SLO 指标与数据隔离模型；
2. **L2 领域阶段与子域链路 (Domain Stage)**：按业务生命周期或单向数据流拆分为自洽子域（如：接入鉴权、分流计算、会话管道、结单归档）；
3. **L3 原子单元与状态机 (Atomic Unit & FSM)**：将子域解构为最小独立单元（单一接口/DB 变更、并发锁粒度与单个状态跃迁），在此层级开展低认知负荷的针对性设计。

### 2.2 向上整体串联闭环检查 (Bottom-Up Holistic Closure Audit)
各 L3 单元设计完成后，**严禁散装交付**，必须将子模块端到端串联，执行三大闭环门禁自查：

| 闭环维度 | 核心审计目标 | 常见缺陷与防御指标 |
| :--- | :--- | :--- |
| **契约拓扑闭合 (Contract Closure)** | 上游 L3 的输出报文/事件，必须 100% 满足下游 L2/L3 的输入契约 | 杜绝下游缺少关键参数（如缺少租户 ID、TraceID 丢失）引发断链。 |
| **逆向补偿闭合 (Compensation Closure)** | 任一子单元发生超时、幂等冲突或断网时，具备完整逆向补偿时序 | 杜绝产生悬挂半事务（如扣款成功但履约失败未触发自动退款）。 |
| **状态机终态闭合 (Finite State Closure)** | 状态机拓扑必须形成闭环，所有状态均具备合法退出条件 | 严禁出现“只进不出”的黑洞状态、不可达的孤儿分支与死循环。 |

## 3. 技术方案设计标准交付模板 (TDD / RFC Template)


技术方案必须严格按照以下 Markdown 模板编写交付：

```markdown
# 🏛️ [功能模块名称] 技术架构方案设计 (Technical Design Document)

## 1. 业务场景与需求收敛 (Socratic Refinement)
- **需求概述**：[简明扼要说明本次设计解决的核心业务价值]
- **核心决策待确认点 (若需求模糊)**：
  - [ ] 待确认点 1：[明确列出需用户拍板的技术/业务分支，如选择 Redis ZSet 还是自研发号器]
  - [ ] 待确认点 2：[明确列出性能、事务边界或降级约束]
- **设计边界**：明确 In-Scope（本次交付）与 Out-of-Scope（明确不做的延伸项）。
- **性能与容量指标**：预期并发（QPS/TPS 峰值）、数据增长估算、时延要求（P99 < 200ms）。

## 2. 领域建模与数据存储设计 (Data Architecture)
- **库表结构与实体关系 (ER)**：核心字段、主键生成策略、唯一索引与分表规划。
- **缓存与状态存储 (Redis)**：分环境 Key 命名空间与 TTL。

## 3. 业务流程、时序交互与状态机 (Workflow & State Machine)
- **核心业务时序图 (Mermaid Sequence)**：严格双引号连线与防崩语法。
- **有限状态机跃迁图 (FSM State)**：覆盖正向流、逆向流与超时闭环。

## 4. 复杂算法与数学公式推导 (若涉及)
- 业务数学模型与标准 LaTeX 公式推导，给出定义域与输入输出边界。

## 5. 健壮性、幂等与异常补偿方案 (Robustness & Fallback)
- **幂等与防并发竞态**：Idempotency Key 与分布式锁粒度。
- **兜底、重试与补偿策略评估**：明确副作用并由用户拍板。

## 6. 实施路线与可验证微任务拆解 (Bite-Sized Verifiable Tasks)
- 拆解为 10~20 分钟粒度的原子任务，严格附带 Target Files 与 Automated Verification 命令。
```

## 4. 架构决策记录 (Architecture Decision Record, ADR)

在重大选型或架构折中时，必须在方案中保留 ADR 决策块：

| 模块 | 规范要求与示例 |
| :--- | :--- |
| **Context (背景上下文)** | 面临什么业务挑战与性能约束？（如：订单履约状态流转高频写倾斜） |
| **Decision (最终裁定方案)** | 选用了哪种技术路线/设计模式？（如：采用 Redis Lua 原子预判 + RocketMQ 延迟双检） |
| **Rejected Alternatives (被否决的备选方案与原因)** | **方案 B (已否决)**：本地轮询扫表。原因：数据库 CPU 占用超标，高并发下存在长事务锁表风险。 |
| **Consequences & Trade-offs (代价与妥协)** | 带来了哪些已知限制？如何防范技术债？（如：需保障 Redis 与 MQ 的高可用探针） |
